# Follow-up: owner-scoped flows, honest phone payouts, real settings save

This pass re-reviews the fixes for ten findings from the prior review (3 HIGH, 3 MEDIUM, 4 LOW) and looks for regressions the fixes introduced. The flow store is now owner-scoped with explicit unscoped escape hatches for the public capture path; phone payouts in sandbox are recorded as failures instead of being silently dropped; the settings page now persists through Clerk; payouts carry a stable id; analytics buckets by real calendar day; and the stats route picks a single money source. Most fixes are correct as described. Two problems the fixes introduced are blocking.

Watch for: the public **`/pay/[id]` page fetches `GET /api/flows`, which is now auth-gated and owner-scoped** — contributors are unauthenticated, so the fetch returns 401 and every public payment link renders "Flow not found" (confirmed, blocking). And Clerk v6's `auth()` is called in nine route handlers but there is **no `middleware.ts` running `clerkMiddleware()`** — in v6 that makes `auth()` throw at runtime rather than return `{ userId: null }`, so the gated routes 500 instead of serving data or returning 401 (likely, blocking). A third, lower issue: the stats "Available balance" note mixes the flow-store figure into the PayPal branch, reintroducing a cross-source inconsistency the fix was meant to remove (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The owner-scoping fix (finding 1) is correctly implemented in the store and on all nine owner-facing routes: each reads `userId` from `auth()`, returns 401 when absent, and passes `userId` into `getAllFlows`/`updateFlow`/`deleteFlow`. Capture correctly uses the unscoped helpers. But the scoping change broke the one legitimately public read path: the `/pay/[id]` checkout page loads its flow via `GET /api/flows`, which now requires a session and only returns the caller's own flows. There is no public single-flow endpoint to replace it, so public payment links no longer resolve.

Separately, the whole auth-gating strategy depends on `auth()` behaving, and in Clerk v6 `auth()` only works when `clerkMiddleware()` is active. No `middleware.ts` exists in the project (confirmed — only compiled `.next` artifacts, none referencing Clerk). This predates these edits in the sense that no middleware was ever added, but the fixes newly depend on `auth()` across nine routes, so the gap now gates the entire dashboard API.

The phone-payout fix (finding 2) is correct: `disburseFlowPayouts` computes `recipientType` per payout, records sandbox phone attempts as explicit failures, and only returns `"Paid out"` when at least one payout was attempted and all succeeded. Both the approve and capture routes flip only successfully-disbursed payouts to `paid`.

The settings fix (finding 3) is correct: `handleSave` awaits `user.update({ firstName, lastName })` with a saving flag and error capture, and a `useEffect` keyed on `isLoaded`/`user` seeds the form once Clerk hydrates.

The stable-id (finding 4) and analytics-bucketing (finding 5) fixes are correct. The stats single-source fix (finding 6) is mostly correct, but the "Available balance" note still injects `flowCollected` into the PayPal branch, so the balance (PayPal) and its caption (flow store) can disagree.

The LOW findings (7–10) are resolved, except the `img` prop on `UseCaseCard` which is still declared but unused.

### Owner-scoping: store and routes (finding 1 — resolved, but see pay-page regression)

`src/lib/store.ts` is cleanly split. `getAllFlows(ownerId)` filters by owner; `updateFlow(id, ownerId, patch)` and `deleteFlow(id, ownerId)` both require an owner match and return null/false when the flow is missing or owned by someone else — callers can't distinguish the two cases, which is the right disclosure posture. The unscoped reconciliation helpers (`getFlowByIdUnscoped`, `updateFlowUnscoped`) are documented as internal-only.

All nine owner-facing routes gate consistently:

```
auth() → userId null? → 401 : getAllFlows(userId) / updateFlow(id, userId, …) / deleteFlow(id, userId)
```

`flows/route.ts`, `flows/[id]/route.ts`, `flows/approve/route.ts`, `stats`, `payments`, `activity`, `build-flow`, `send`, `invite` all follow this. `build-flow` sets `ownerId` from the session via `toDashboardFlow(plan, userId)`. The approve route first confirms ownership with `getAllFlows(userId).find(...)` before disbursing, then updates through `updateFlow(flowId, userId, …)` — so a user can't approve someone else's flow.

The capture route is the one intentional public path and uses `updateFlowUnscoped`/`getFlowByIdUnscoped`. Its mutation surface is tightly bounded: it only ever adds the captured amount to `collected`, increments `contributors`, and — on goal completion — flips payout states to `paid` for labels that actually disbursed. A caller cannot rename a flow, change goals, retarget recipients, or move money to an arbitrary account through capture; the recipients come from the stored flow, not the request. The request supplies only `orderId` and `flowId`, and the amount is read from PayPal's capture response, not the body. The abuse ceiling is "replay a captured order against a flow you don't own," which inflates `collected`/`contributors` and can trigger a premature payout to the flow's *own* configured recipients — worth noting, but not an exfiltration path.

The regression is on the read side. `src/app/pay/[id]/page.tsx` (lines ~62–75) loads the flow with:

```ts
fetch("/api/flows")
  .then((r) => r.json())
  .then((d) => setFlow((d.flows ?? []).find((x) => x.id === id) ?? null))
```

`GET /api/flows` now returns 401 for anyone without a session and, for a signed-in user, only *their* flows. A contributor following a share link is neither. The promise resolves with no `flows` array, `find` yields `undefined`, and the page renders "Flow not found" — the public payment flow is dead. There is no public single-flow endpoint (confirmed by searching the `api` tree). The fix needs a public `GET /api/flows/[id]` backed by `getFlowByIdUnscoped`, returning a minimal projection (name, goal, collected, contributors, payouts preview, the PayPal order resource) rather than the whole record.

### Clerk middleware gap (new, blocking)

Every gated route imports `auth` from `@clerk/nextjs/server` and does `const { userId } = await auth()`. The gating assumes `auth()` returns `{ userId: null }` for anonymous callers. In Clerk v6 (`@clerk/nextjs@^6.12.12` here), `auth()` only functions when `clerkMiddleware()` has run for the request; without it, `auth()` throws (`Clerk: auth() was called but Clerk can't detect usage of clerkMiddleware()`). There is no `middleware.ts` in the project — only compiled `.next/server/middleware.js`, which contains no Clerk references. So in practice the gated routes would 500 on every request, not cleanly 401/serve.

This is adjacent to the diff rather than strictly inside it — no middleware was added or removed here — but the fixes newly route all dashboard data access through `auth()`, which turns a dormant setup gap into a live outage across the API. A `middleware.ts` running `clerkMiddleware()` with a matcher that protects dashboard/API routes while leaving `/pay/*` and `/api/capture` public resolves both this and sits alongside the pay-page fix.

### Honest phone payouts (finding 2 — resolved)

`disburseFlowPayouts` in `src/lib/paypal.ts` now derives `recipientType` from each recipient (`"@"` ⇒ EMAIL else PHONE). Sandbox phone payouts short-circuit into an explicit failed `PayoutResult` with a clear message instead of being skipped. The status logic is correct:

```ts
const allSucceeded = results.length > 0 && results.every((r) => r.ok);
finalStatus = allSucceeded ? "Paid out" : "Needs approval";
```

A flow whose payouts are all already paid yields `results.length === 0` → `"Needs approval"`, so re-approving a fully-paid flow reports "Needs approval" rather than "Paid out" — a benign edge, not a regression. Both consumers flip only `paidLabels` (successful disbursements) to `paid`:

```ts
const paidLabels = new Set(results.filter((r) => r.ok).map((r) => r.label));
f.payouts = f.payouts.map((p) => paidLabels.has(p.label) ? { ...p, state: "paid" } : p);
```

One latent coupling: `paidLabels` keys on `label`, while the rest of the fix moved recipient editing to key on stable `id`. Two payouts sharing a label (the schema doesn't forbid it) would both flip to `paid` when only one disbursed. Low likelihood, but since the stable-id machinery now exists, the paid-set could key on it too.

### Stats single-source (finding 6 — mostly resolved; note inconsistency)

`stats/route.ts` picks one source: PayPal when `listTransactions()` returns rows, else the flow store, else an empty payload. `balance = max(0, collected - paidOut)` uses that source's figures. The remaining defect is the note on "Available balance":

```ts
note: flowCollected > 0 ? `${usd(flowCollected)} collected across flows` : collectedNote,
```

In the PayPal branch, `balance`/`collected` come from PayPal but this note reports the flow-store total (`flowCollected`). So the balance value and its caption can describe different money — the exact cross-source mismatch the fix set out to remove. The note should use the chosen source's collected figure (or `collectedNote`).
