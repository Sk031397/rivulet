# Rivulet dashboard — flows, send, analytics, settings, landing review

A read-only quality pass over the recently-built dashboard features (flows + recipient editing, Send, overview analytics, settings) and the landing page, plus the API routes and stores behind them. The frontend is polished and the UX is thoughtful, but the backend has one structural problem that dominates everything else: every `/api/*` route is unauthenticated and the `flows.json` store is a single global file shared across all visitors. Layered on top of that are a confirmed phone-payout dead-end, a label-keyed data model with no stable id, a few analytics bucketing bugs, and a Settings page that silently discards everything the user types.

**Watch for:** API routes have no Clerk session check and the file store is global — any visitor sees and mutates every other user's flows (confirmed, high). Phone recipients can be set on flow payouts but `disburseFlowPayouts` silently skips any non-email recipient, so approving a phone-only payout reports success while paying nobody (confirmed, high). Settings "Save changes" only writes to local React state — nothing persists to Clerk or a backend (confirmed, high). Analytics trend buckets sort lexically on pre-formatted date strings and the stats `Math.max` logic can double-count or mismatch (confirmed, medium).

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend is the strong half of this codebase. The flows page, Send form, and analytics panel are built with care: AG Grid is wired up correctly, the recipient combobox has real keyboard navigation and ARIA wiring, the Send form has thorough client-side validation with good inline feedback, and the landing page respects `prefers-reduced-motion`. The custom components are mostly accessible, with a few gaps noted below.

The backend is where the gaps concentrate, and they are not subtle. Despite Clerk middleware existing (`src/proxy.ts`, the Next 16 name for `middleware.ts`), it only calls `auth.protect()` on `/dashboard(.*)` — the API routes run through the matcher but are never gated, and none of them call `auth()` themselves. Combined with `src/lib/store.ts` being a single global `flows.json` with no per-user scoping, every flow is visible and editable by anyone who can reach the API. For a hackathon demo this may be acceptable, but it should be a conscious decision, not an accident.

The phone-recipient feature is a half-connected wire. The Send page and the flow recipient editor both now accept and validate phone numbers, and `createPayout` supports a `PHONE` recipient type. But `disburseFlowPayouts` — the function behind both auto-disbursement on goal completion and manual approval — guards with `p.recipient.includes("@")`, so any phone recipient is silently skipped. The UI reports the flow as "Paid out" regardless. The Send route handles this honestly (it fail-fasts on phone in sandbox); the flow approval path does not.

The data model keys payout recipient updates by `label` (`PATCH /api/flows/[id]` and the edit UI both match on `p.label`). Two payouts sharing a label, or a label that changes, corrupts the mapping. There is no stable payout id.

The analytics have two real bugs: trend buckets are keyed and sorted on already-formatted display date strings, so `slice(-10)` returns a lexical slice rather than the ten most recent days; and the stats route takes `Math.max` of PayPal totals against flow-store totals independently for collected and paid-out, which can mix two unrelated data sources into one impossible balance.

Settings is a visual shell: `handleSave` writes to a local `saved` object and shows a toast, but never calls Clerk's `user.update()` or any API. First/last name, email, and phone edits vanish on reload.

<summary>Issues (12)</summary>

1. **Unauthenticated API + global store** — `/api/flows`, `/api/send`, `/api/stats`, `/api/capture`, `/api/flows/approve`, `/api/build-flow` never check the Clerk session; `store.ts` is one global `flows.json`. Scope the store per-user and add `auth()` checks (or consciously document this as demo-only).
2. **Phone payouts silently dropped on approval** — `disburseFlowPayouts` skips any recipient without `@`, but the flow is still marked "Paid out". Either support PHONE in disbursement or block setting phone recipients on flow payouts and surface a skipped-count in the result.
3. **Settings save is a no-op** — `handleSave` only updates local state; name/email/phone never persist to Clerk. Wire to `user.update()` / a backend, or remove the fields that can't be saved.
4. **Payouts keyed by label, no stable id** — `PATCH /api/flows/[id]` and the edit UI match on `p.label`; duplicate or renamed labels corrupt recipient assignment. Add a stable payout id.
5. **Trend buckets sort on formatted date strings** — `AnalyticsPanel` keys buckets by `p.date` (a display string) and `slice(-10)` lexically, so the chart isn't the ten most recent days. Bucket by an ISO/sortable date, then format.
6. **Stats `Math.max` mixes data sources** — `stats/route.ts` takes `Math.max(ppCollected, totalCollected)` and `Math.max(ppPaidOut, totalPaidOut)` independently, producing a balance that reflects neither source consistently. Pick one source of truth per figure.
7. **Phone recipients written to flow but undisbursable** — `PATCH` validates and stores phone recipients that `disburseFlowPayouts` will never pay. Align validation with what disbursement actually supports.
8. **Floating-filter datalist has no visible label** — `AutocompleteFloatingFilter` relies on `aria-label` only; fine for SR but the raw colId (`"collected"`) is exposed as the label. Use the human header name.
9. **Modals don't trap focus or restore it** — `FlowPanel`, `ModalShell`, and `DemoModal` set `aria-modal` and handle Escape but don't trap Tab focus inside or return focus to the trigger on close. Add a focus trap.
10. **`addContact` persists unverified input** — Send page calls `addContact(cleanRecipient)` before confirming the payout settled; a failed/typo recipient still lands in the address book. Persist only on success, or allow removal.
11. **Confirm-password toggle shares state** — in `PasswordModal` the "Confirm new password" field reuses `showNext`, so toggling visibility on the new-password field also reveals the confirm field unexpectedly. Give it its own state.
12. **No currency/locale safety on money math** — amounts are summed as floats and formatted ad hoc; `collected + capture.amount` uses `toFixed(2)` re-parse in one place but not others. Centralize money handling to avoid drift.

### Auth stub and the global flows.json store

This is the finding that reframes everything else. `src/proxy.ts` is the Clerk middleware (Next 16 renamed `middleware.ts` to `proxy.ts`, so the file name is correct and the middleware does run). But the gate is:

```ts
const isProtected = createRouteMatcher(["/dashboard(.*)"]);
export default clerkMiddleware(async (auth, req) => {
  if (isProtected(req)) await auth.protect();
});
```

The `config.matcher` deliberately includes `/(api|trpc)(.*)`, so the middleware *executes* on API requests — but `isProtected` only matches `/dashboard`, so `auth.protect()` never fires for `/api/*`. None of the route handlers (`flows/route.ts`, `flows/[id]/route.ts`, `send/route.ts`, `stats/route.ts`, `capture/route.ts`, `flows/approve/route.ts`, `build-flow/route.ts`) call `auth()` or read a session. Every one is reachable unauthenticated.

`src/lib/store.ts` compounds this: it reads and writes a single `flows.json` at the project root with no user dimension anywhere in the `Flow` type (`src/data/dashboard.ts`). So the store isn't just unauthenticated — it's global. Every user who loads `/dashboard` sees the same flows, and `POST /api/send` or `POST /api/flows/approve` will disburse real PayPal money against flows created by anyone. `GET /api/flows` is also the source for the address book (`fetchFlowContacts` in `addressBook.ts`), so recipient emails/phones leak across users too.

If this is a deliberate single-tenant hackathon demo, that's a legitimate choice — but it should be stated, because the Clerk integration on the `/dashboard` pages strongly implies multi-user. At minimum, add `auth()` to each route and key the store by `userId`.

### Phone payouts: a silent dead-end on the approval path

The Send route handles phone honestly:

```ts
if (recipientType === "PHONE" && process.env.PAYPAL_ENVIRONMENT !== "PRODUCTION") {
  return Response.json({ error: "Phone-number payouts aren't supported in the PayPal sandbox..." }, { status: 400 });
}
```

The flow approval path does not. `disburseFlowPayouts` in `src/lib/paypal.ts`:

```ts
for (const p of flow.payouts) {
  if (!p.recipient || !p.recipient.includes("@") || p.state === "paid") continue;
  ...
}
const anySuccess = results.length === 0 || results.some((r) => r.ok);
return { results, finalStatus: anySuccess ? "Paid out" : "Needs approval" };
```

A phone recipient fails the `includes("@")` guard and is skipped without a result entry. Worse, `anySuccess` is `true` when `results.length === 0`, so a flow whose payouts are *all* phone numbers returns `finalStatus: "Paid out"` with zero disbursements. Both `/api/capture` (auto-disburse on goal) and `/api/flows/approve` then set every payout state to `"paid"`. The UI in `FlowPanel` shows "Paid out" and the approve-results card shows `0/0 sent` with "No recipient emails on this flow" — but the flow is now permanently marked paid.

Meanwhile `PATCH /api/flows/[id]` explicitly validates and *accepts* phone recipients (`cleanRecipient` runs `PHONE_RE`), and the recipient editor placeholder says "Email or phone number". So the product invites users to set phone recipients that can never be paid through the flow path. Either teach `disburseFlowPayouts` to pass `recipient_type: "PHONE"` (it's already a supported param on `createPayout`), or reject phone recipients at the flow-edit boundary and tell the user why — and in either case, `disburseFlowPayouts` should return a skipped list so the caller never marks unpaid payouts as paid.

### Payouts keyed by label

The recipient-edit round trip keys entirely on `label`. In `FlowPanel.saveRecipients`:

```ts
const payload = flow.payouts.map((p) => ({ label: p.label, recipient: ... }));
```

and in `PATCH`:

```ts
const payout = f.payouts.find((p) => p.label === u.label);
if (payout) payout.recipient = u.recipient || undefined;
```

`Payout` (in `dashboard.ts`) has no id. The AI-generated flows come from `build-flow` with free-text labels, so two payouts labelled e.g. "Volunteers" would both receive the first match's recipient, and a later rename of a label silently orphans its recipient. A stable `id` on `Payout`, generated at creation and used as the map key everywhere, removes a whole class of silent corruption.

### Analytics trend bucketing and stats Math.max

Two confirmed correctness bugs.

Trend buckets in `AnalyticsPanel`:

```ts
for (const p of payments) {
  const key = p.date; // dates are pre-formatted strings from the API
  ...
}
return Array.from(byDay.values()).slice(-10);
```

`key` is a pre-formatted display string, and `byDay` is a plain `Map` (insertion-ordered, not date-sorted). `slice(-10)` therefore returns the last ten *inserted* day-buckets in whatever order the payments arrived, not the ten most recent calendar days. If the API returns payments newest-first, the chart shows the oldest ten of that page. Bucket on a sortable date (ISO or epoch), sort ascending, then slice and format for display.

Stats in `stats/route.ts`:

```ts
const collected = Math.max(ppCollected, totalCollected);
const paidOut = Math.max(ppPaidOut, totalPaidOut);
const balance = Math.max(0, collected - paidOut);
```

`collected` and `paidOut` are maxed independently against two unrelated sources (live PayPal reporting vs the flow store). You can end up with `collected` taken from PayPal and `paidOut` taken from the flow store, so `balance` reflects neither. The `note` on "Available balance" then says "$X collected across flows" using `totalCollected` even when the headline used `ppCollected`. Pick one source of truth per card, or reconcile them explicitly rather than per-figure `Math.max`.

### Recipient combobox and address book

`RecipientAutocomplete` is the best-built custom component here: `role="combobox"`, `aria-expanded`/`aria-controls`/`aria-activedescendant`, arrow-key navigation with wraparound, Enter to select, Escape to dismiss, `onMouseDown` + `preventDefault` so selection beats input blur, and outside-click close. The one gap is that `aria-activedescendant` points at an option id but the list items don't scroll into view on arrow navigation — fine for a 6-item capped list, worth noting if that cap grows.

One behavioral concern in the Send flow: `addContact(cleanRecipient)` runs inside the success branch, but the "success" is `res.ok` on the payout request — which for a real payout can still resolve to an `UNCLAIMED`/pending item. That's acceptable, but a mistyped-yet-valid address (wrong-but-well-formed email) is permanently saved to the local address book with no UI to remove it. `addressBook.ts` has `addContact` but no `removeContact`.

### Floating-filter datalist

`AutocompleteFloatingFilter` is a clean idea — a `<datalist>` populated from the distinct column values, driving AG Grid's parent text/number filter. The accessibility gap is the label: `aria-label={`Filter ${column.getColId()}`}` exposes the raw column id (e.g. `"collected"`) rather than the header name. The component already receives `field`; using the column's human header name would read better to a screen reader. Also note the numeric branch applies an `equals` filter — typing a partial number like "1" into the Collected filter matches only the exact value 1, not "contains 1", which may surprise users who expect the text-filter behavior the name "Autocomplete filter" implies.

### Modals: Escape and scroll-lock yes, focus trap no

`FlowPanel`, the Settings `ModalShell`, and the landing `DemoModal` all correctly set `role="dialog"` + `aria-modal="true"`, handle Escape, and lock body scroll (`DemoModal` even saves/restores the previous overflow value — nice). What's missing across all three is focus management: Tab is not trapped inside the dialog, and focus is not moved into the dialog on open or restored to the trigger on close. Keyboard and screen-reader users can tab out into the page behind the backdrop. A small shared focus-trap hook would fix all three at once.

### Settings is a visual shell

`handleSave` is the whole persistence story:

```ts
const handleSave = () => {
  setSaved({ firstName, lastName, email, phone });
  setShowToast(true);
  setTimeout(() => setShowToast(false), 3000);
};
```

It writes to a local `saved` object (used only by `handleCancel`) and shows a "Changes saved" toast. Nothing reaches Clerk — no `user.update(...)`, no API call. The fields are *seeded* once from Clerk (`clerkFirstName`, etc.) but edits never flow back. Same for the password modal, 2FA modal, add-payment-method, and delete-account, which are all front-end simulations (the delete button literally `alert()`s "would be processed by your backend"). For a demo that may be intentional, but the "Changes saved" toast actively lies to the user. Either wire profile save to `user.update()` (Clerk supports first/last name updates client-side) or relabel these as previews.

### Landing page

`Hero.tsx`, `FlowMock.tsx`, and `UseCaseCard.tsx` are solid. The demo modal portals to `document.body`, locks scroll, restores overflow, and handles Escape. `globals.css` ends with a thorough `prefers-reduced-motion` block that neutralizes the many keyframe animations — good, given how animation-heavy `FlowMock` and the blob parallax are. Font setup in `layout.tsx` uses `next/font` with `display: "swap"` and CSS variables wired to Tailwind's `@theme`, which is the correct modern pattern. Two small notes: the `video` in `DemoPlayer` autoplays with sound-capable `controls` but no `muted`, so autoplay may be blocked by browsers (and the eslint-disable for `media-has-caption` acknowledges there's no caption track); and `UseCaseCard` accepts an `img` prop that is destructured out and never used, alongside `fallback` which is — dead prop worth removing.
